# Agent Note: Auto Mode Tool Review

Status: proposed

## Problem

Cooper 的 `auto` 会直接批准工具调用，`ask` 则把写文件、命令执行和网络请求交给用户。修复失败测试这样的任务需要反复读代码、改文件、运行命令。用户需要让常规步骤连续运行，同时保留对命令实际副作用和任务授权范围的检查。Cooper 的 shell 以当前操作系统用户身份运行，工作目录校验只能约束启动位置。[运行时权限模式](../../implemented/feature/2026-11-09-runtime-permission-modes.md) · [交互式工具审批](../../implemented/feature/2026-11-11-interactive-tool-approvals.md)

## Proposal

将 `auto` 改为逐调用审批。权限规则处理可直接判定的动作，独立模型审核需要理解用户意图或命令副作用的动作。借鉴 Claude Code 的实现，审核输入以用户原话和实际工具调用为主，固定审核策略由宿主提供。Cooper 使用现有 shell 执行器，已批准的命令继续以当前用户权限运行。界面和启动提示说明这个权限边界。[Claude Code Auto 工程说明](https://www.anthropic.com/research/claude-code-auto-mode)

### 运行时决策

在 `runAgent()` 解析工具入参后、派发执行前，由 `PermissionPolicy` 决定直接执行、拒绝、人工确认或独立审核。内置只读工具和通过路径、目标与现有预览校验的普通文件编辑可直接执行。工作区外的文件路径越界时拒绝。写入项目指令、Cooper 权限配置、Git 元数据和凭据文件时，要求人工确认。具备外发或不可逆副作用的操作按宿主规则进入人工确认。通用 shell 默认进入独立审核。内置网页工具和通用 MCP 调用首版沿用现有人工审批边界。

程序以实际解析后的路径、命令、参数和效果匹配，工具描述、主模型的解释及 MCP 自报标签都只作为数据。自动与人工审批复用预览、执行前复查及会话派发边界。审核只绑定当前调用和用于判定的证据快照；路径、命令、工作目录、已审脚本或相关用户授权变化时，重新判定。`plan`、`ask`、只读恢复以及现有的派发记录失败处理沿用各自的权限边界。[工具审批入口](../../../../packages/core/src/agent.ts) · [中断与恢复](../architecture/2026-11-18-desktop-turn-interruption-and-recovery.md)

### 审核请求与结论

宿主默认复用用户已配置的 Provider、端点和当前模型，发起独立审核调用。用户可以在用户级配置指定同一端点的审核模型。审核请求使用固定系统策略，动态内容按来源组织，工具列表为空。每次请求包含以下信息。

- **授权**。选取有关的用户原话，保留后续追加的限制、批准与撤回。项目指令和工作区数据可提供背景或收紧约束，授权扩展来自用户或宿主可信配置。
- **待执行动作**。保留实际工具名、完整命令、shell、解析后的工作目录，以及本次执行的权限事实。命令未经操作系统沙箱限制时，明确传达这一点。
- **相关历史调用**。保留涉及待审动作的工具名和参数，例如此前写入待执行脚本的 `write` 或 `edit`。过滤掉主助手的推理、进度说明、调用自述和原始工具输出。
- **宿主核对的必要事实**。按需读取小范围的本地证据，标注来源。例如 `npm test` 可带上工作目录实际读取的 `test`、`pretest`、`posttest`，以及相关脚本是否由本轮修改。限制证据大小，用结构化字段标明截断、缺失和脱敏。关键证据缺失时转人工。

采用 Claude Code 的筛查与复审思路。快速审核只返回放行或转细审。两阶段共用同一份调用和证据，细审返回 `allow`、`ask` 或 `deny` 以及一条简明理由。首个可用实现可以对每次请求直接调用细审；快速放行路径以对照评估为启用条件。输出由宿主严格校验；放行只在程序允许送审的范围内生效。超时、取消、无效结果、`ask` 和 `deny` 各自有明确结果。交互端在 `ask` 或审核不可用时可以转人工，无头端拒绝该调用。明确拒绝的操作交回主助手并说明原因，只允许在现有授权内改用不同做法。审计记录保留结论、来源和精简理由，审核请求本体和私有推理沿用最小留存原则。[Claude Code 审核输入与两阶段设计](https://www.anthropic.com/research/claude-code-auto-mode#design-decisions)

### 运行专用临时目录

宿主为每次运行在系统临时目录下创建专用子目录。内置文件工具增加显式的临时目录范围，已有调用默认仍解析到工作区。两个范围分别以宿主分配的真实根校验路径及符号链接和 Windows junction。这个变化需要同步修订仓库的单工作区根约束。shell 子进程的 `TMPDIR`、`TMP`、`TEMP` 指向该目录，作为遵循这些变量的工具的默认位置。宿主在工具和子进程结束后清理自己的目录，需保留的输出由任务写入工作区。崩溃恢复处理须核对目录归属及运行状态。[路径包含性](../../implemented/bug-fix/2026-11-11-workspace-real-path-containment.md)

### 生效与迁移

`--mode auto` 和交互模式切换继续由用户显式启用，恢复会话继续按现有规则处理。版本说明明确已存在的 `--mode auto` 从全放行变为逐调用判断，列出脚本在无头模式收到拒绝时的处理方式。TUI、headless 和 Desktop 由同一个 Core 决策入口执行；宿主提供审核请求的 Provider 和人工审批能力。模式通知继续追加到会话，保留现行的前缀缓存行为。[进程级自动授权](../../implemented/feature/2026-11-11-per-process-auto-authorization.md)

## Alternatives considered

**全放行或只靠命令前缀。** 全放行让每个命令继承用户系统权限。按前缀批准也难以理解脚本入口、复合命令以及本轮用户的限制。窄范围的程序判断适合已知效果的调用，其他调用需要审核实际动作。

**转发完整对话和工具输出。** 完整记录能补足上下文，同时会放大传输范围和注入面。保留用户原话、实际调用和有来源的少量证据，能审查写后执行、授权边界和关键副作用。

**随应用分发或训练审核模型。** 独立调用现有 Provider 已能建立审核边界。模型分发、训练和自建端点会增加维护、评估与使用成本，后续模型选择由样本上的漏放、误拦和延迟数据决定。

**授权整个系统临时目录。** 共享临时目录还包含其他程序的内容。宿主分配的单次运行子目录提供所需的临时工作空间和清理边界。

## Acceptance criteria

- 用户启用 AUTO 后，Cooper 在没有另配审核端点的情况下完成一次改代码、审核并运行测试、根据结果继续修复的任务。
- 用户说「运行现有测试，别安装依赖」时，审核请求能从实际 `pretest` 发现安装动作。后续用户限制和撤回可以覆盖此前的授权。
- 预览后替换脚本、修改调用入参、切换符号链接或撤回授权会使旧批准失效。审核指令注入、模糊命令、审核超时、无效输出和中断恢复有明确覆盖。
- 工作区与本次运行的临时目录均可正常读写；共享临时目录的其他路径、其他运行的临时目录以及跨根链接无法获得自动授权。
- CLI、Desktop 与 headless 的调用按同一策略分类。无头需要人工决定时拒绝并报告是哪次调用，模式仍需显式开启。
- 用代表性命令和上下文对照人工标注，记录自动批准覆盖率、误拦、漏放和延迟，再决定快速放行的可用范围。

## Risks

审核模型可能误判，放行的 shell 命令仍有当前用户具备的系统权限。静态证据也无法证明动态脚本的全部副作用。固定权限规则、按次复查和证据不足时转人工限制了自动批准范围。审核会增加端点调用、延迟和费用，并向用户配置的服务发送有关命令与必要证据。端点收到的材料需要有明确预算和脱敏规则，尤其是命令参数、路径与脚本内容。临时目录和工具环境变量不会改变 shell 的系统权限。旧脚本切换到新 AUTO 语义后可能需要调整授权范围或处理拒绝结果。
