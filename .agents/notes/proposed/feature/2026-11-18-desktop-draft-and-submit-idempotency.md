# Agent Note: Desktop Drafts and Idempotent Submission

Status: proposed

## Problem

Desktop 发送前清空输入框。切换会话时，同一个输入框可能把上一条草稿带到新会话。写入用户消息前失败会丢稿，写入后确认丢失会让用户误以为未发送并重发同一任务。用户需要在切换会话和应用退出后找回草稿，发送结果也需要可核对。 [输入框行为](../../../../apps/desktop/src/renderer.ts) · [提交入口](../../../../apps/desktop/src/runtime.ts)

## Proposal

每个已有会话有自己的草稿，每个工作区先保留一份尚未创建会话的草稿。「新对话」打开对应草稿，首次提交成功以后把它归入已创建会话。草稿保留文本及换行。用户输入草稿、主进程写入用户消息和 Agent 开始执行是三个独立阶段。

### 存储和提交顺序

Desktop 主进程把草稿保存在 Electron `userData` 下的专用目录。目录和文件使用当前用户私有权限，POSIX 采用 `0700` 目录和 `0600` 文件，Windows 验证目录的用户 ACL 能提供等效范围。会话和工作区作为稳定的草稿键，文件名由主进程生成。渲染器经 IPC 读写原始文本和草稿修订号。

普通输入可合并保存，切换会话、关闭窗口及发送前立即处理当前修订。使用同目录临时文件、同步写入和原子替换。失败时保留先前有效版本和界面上的新内容，并提示保存失败。损坏文件不能证明草稿为空或发送成功。显示可找回的版本并暂停自动清理。

1. 用户点击发送时，主进程先固化本次提交的 `sessionId`、`requestId`、草稿修订号与原始文本。首次提交提前分配稳定的会话 ID。该记录同步保存成功后才允许继续。
2. 主进程取得会话写入权，按请求 ID 查对原始日志。首次追加将请求 ID 和回合 ID 放在**同一条用户消息记录的元数据**中，按 v2 契约同步写入。已有相同 ID 和内容返回原确认。相同 ID 的内容冲突报错。申请提交和查询确认使用 [会话写入互斥](../architecture/2026-11-18-session-writer-exclusion.md) 下的同一份权威记录。
3. IPC 返回接收确认及实际会话和回合 ID。收到确认后只清理匹配的待提交修订，不覆盖等待期间写入的新草稿。主进程可以启动 Agent 工作，进度由独立运行事件展示。窗口若先收到运行事件，可按请求 ID 暂存，确认后按运行标识合并。
4. 重启后对账。已找到确认就恢复原消息及会话，经过可信核对可证明未提交时显示草稿并允许用户重发。日志不可读或处于未知状态时保留原草稿与请求 ID，明确标注「发送状态待确认」，等待重新核对。恢复草稿或打开待确认会话不发模型请求。

### 第一阶段

Desktop 的 v1 路径已接入按会话保存的草稿、发送前的待确认标记和写入后的 `accepted` 事件。渲染器可以在模型退出前清空输入框并展示已入会话的用户消息。原有 `send` 响应仍用于本次运行结束。重开时若有待确认标记，提示用户检查历史，再由用户决定是否继续编辑。下节的请求 ID 对账和独立提交响应随 v2 契约评审与交付。

### IPC 与历史兼容

| 调用 | 最小契约 |
| --- | --- |
| `readDraft(key)`、`saveDraft(key, revision, text)` | 主进程返回保存的文本、修订号和待提交标识，旧修订不能覆盖新修订。 |
| `submit({ key, revision, requestId, text })` | 返回 `accepted { sessionId, requestId, turnId }`、`rejected { reason }` 或 `unknown { requestId }`。已接收的消息只写一次，接收确认不等待模型结束。若主进程返回前断开，通过对账查询原请求。 |
| `lookupSubmission(sessionId, requestId)` | 返回已接收、可确认未接收、已撤下或无法确认。对账使用持久化元数据，不比对消息文本。 |

请求标识留在宿主和会话元数据中。对账区分「曾写入」和「仍在有效分支」。常规压缩可以移除有效上下文里的早期消息，确认仍有效。若 [工作区与会话回退](2026-11-12-workspace-and-conversation-rewind.md) 将某个已接收回合撤下，回退记录需要表达对应的回合范围。旧请求 ID 返回「已撤下」，用户再次发起同内容需要新的 ID。 [Core 恢复与日志契约](../architecture/2026-11-18-desktop-turn-interruption-and-recovery.md)

旧 v1 会话也能保留独立草稿和当次发送确认。重新打开后的幂等对账依赖 v2 提交记录和写入互斥。v1 原文件沿用旧读写方式，有未决提交时保留草稿，显示需要手工核对。

## Implementation progress

Desktop v2 把请求 ID、回合 ID 和用户消息写入同一条 JSONL 记录。主进程通过独立的 accepted 事件确认接收，现有 send 调用仍等待本轮结束。重开工作区时若能用草稿中的请求 ID 找到确认，直接打开对应会话。若日志损坏或证据不足，保留草稿供用户核对。有待恢复的回合不会因打开会话而自动运行。回退使旧请求失效的规则随回退功能实现。

## Alternatives considered

**只在 IPC 接收确认时清空。** 能覆盖常规失败且成本低。窗口退出会丢失草稿和待确认身份，重启后无法判断这条消息是否已被接收。

**在渲染器内存或 localStorage 保存请求身份。** 输入偏好使用渲染器存储足够。发送确认要求在追加前有可验证的持久屏障和一致的错误反馈，因此交给主进程管理。

## Acceptance criteria

- 工作区和会话之间切换及重启后，草稿独立且保留原始空格和换行。新草稿修订不会被旧确认清空。
- 分别在保存待提交记录前、保存后但追加前、用户消息同步后但确认前强制退出，重开后恢复到正确状态。重复提交同一 ID 时只存在一条用户消息，损坏记录和存储失败时保存可用文本并显示待确认。
- 验证不同用户的读权限约束。验证普通压缩后仍可对账、回退后旧请求返回已撤下、v1 草稿可恢复且未决提交会提示手工核对。
- 按实际预加载桥验证接收确认早于模型终态，以及确认和运行事件乱序时只显示一份用户消息。运行 `npm run typecheck` 和 `npm test`。

## Risks

草稿可能含源码和凭证，受用户私有存储边界约束。异常退出后的对账依赖草稿和会话记录仍可读取。断电或存储故障可能让状态无法确认，保留待提交内容并等待用户核对可减少重复发送。
