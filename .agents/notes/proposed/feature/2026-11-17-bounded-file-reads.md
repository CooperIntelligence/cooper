# Agent Note: Bounded File Reads and Page Size

Status: proposed

## Problem

模型经常只需要一个函数或错误附近的代码。工具结果会随后续请求重复发送，默认多读的行会反复占用上下文。现有工具先读完整文件，再裁剪返回值。超过读取上限时提示分页，但指定行范围仍会被同一大小检查拒绝。字符截断也可能让提示里的行范围大于实际输出。

## Proposal

用固定大小的流块定位行范围，根据实际返回的最后一行给出下一次 `offset`。输出正文上限沿用 48,000 字符。普通行放不进当前页就留给下一页。超长单行需要明确标出截断位置，并告诉模型如何从下一行继续。页尾只提供已经确认的信息，避免为了总行数扫描整份文件。已经知道相关行号时，工具说明引导模型直接传 `offset` 和 `limit`。

在实验分支把默认页从 400 行改为 200 行，保留显式范围。先对同一批源码比较 120、200、400 行的首屏重量，再比较按已知范围读取和需要翻页的情形。是否采用 200 行取决于整项任务的输入用量、补读次数和结果。首屏数据只能筛选候选页长。

[工作区真实路径校验](../../implemented/bug-fix/2026-11-11-workspace-real-path-containment.md)仍负责路径边界，分页负责读取和输出边界。

## Prototype results

在同步后的 `main` 基础上，使用本地估算器对 core 与 CLI 的 57 个 TypeScript 源文件执行真实读取。

| 页上限 | 首屏平均 token | 首屏需续读的文件数 | 逐页读完的工具调用数 | 每页触发后续请求时，本文件工具正文的累积输入 token |
| --- | ---: | ---: | ---: | ---: |
| 120 | 1,029 | 28 | 126 | 381,976 |
| 200 | 1,388 | 20 | 91 | 273,724 |
| 400 | 1,852 | 6 | 66 | 183,977 |

已知目标行时，6 个固定代码范围各用一次调用，合计约 3,130 token。逐页从文件头查找同样范围时，200 行需要 15 次读取、约 67,803 累积输入 token。400 行需要 10 次、约 56,401 累积输入 token。累积值只计工具返回内容在同一文件内随历史重发的估算，未计工具定义、推理或缓存折扣。

在 Windows 上验证一个 16 MiB 长行样本。首屏只从磁盘读取 64 KiB 就关闭文件流。深页读取在首个流块到达时取消，文件流也关闭。实际模型任务的完成率和供应商用量仍待验证。

## Alternatives considered

**继续整读再切片。** 实现简单，但大文件分页仍会把本次任务不需要的数据读入内存，并依赖文件体积上限。

**直接把默认页缩到 120 行。** 首屏更省，但 Cooper 源码采样中有更多文件需要续读。200 行先用于验证收益与额外模型轮次的取舍。

**缓存重复读取并返回「未变」。** 如果旧结果已被压缩，模型可能正是为了找回内容才重读。先减少每次返回的数据量。

## Acceptance criteria

- 超过 2 MiB 的文本可用现有参数分段读取。对未变动的文件，按返回的 `offset` 翻页时完整行不会跳过或重复。
- 单次输出有界。超长行有明确截断提示，普通行的页尾定位准确。保留现有 LF、CRLF、UTF-8 和零基 `offset` 语义，取消时关闭读取流。
- 报告 200 与 400 的对照结果，说明首屏节省与补页代价有何差别。默认值定案前还需要实际模型任务的完成率和总用量。

## Risks

按行定位较深的 `offset` 仍需扫描此前的文件数据。文件在两次调用之间发生编辑时，旧的行号可能移动。只靠行号也无法续读被截断的同一行。较短的默认页可能促使模型多请求一轮，抵消首屏节省。
