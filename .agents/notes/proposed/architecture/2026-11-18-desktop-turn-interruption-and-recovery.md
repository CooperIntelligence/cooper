# Agent Note: Core Turn Interruption and Recovery

Status: proposed

## Problem

一次用户任务可以包括多次模型请求和一批工具调用。Desktop 当前通过一次 IPC 调用等到整轮退出。模型断线、用户停止和工具结果写入失败容易表现为同一种错误。恢复不完整工具组时，Core 还会把已经写入的工具结果一起移出模型历史，但工具造成的变更可能仍在。 [Desktop 运行时](../../../../apps/desktop/src/runtime.ts) · [现有会话修复](../../../../packages/core/src/session.ts)

## Proposal

Core 按已记录的事实结束或继续回合。每次执行工具前确认派发记录已持久化，每次请求模型前确认工具组的结果已配对。停止、失败与进程退出分别处理。Desktop 通过独立的回合事件展示进度和终态。草稿与提交确认由 [Desktop 草稿与提交幂等](../feature/2026-11-18-desktop-draft-and-submit-idempotency.md) 负责。可写恢复依赖 [会话写入互斥](2026-11-18-session-writer-exclusion.md)。

### 回合、调用与日志契约

| 记录 | 最小字段与语义 |
| --- | --- |
| 用户消息的提交元数据 | `requestId`、`turnId`。放在会话记录外层。一次提交开启一个逻辑回合，后续继续使用同一个 `turnId`。 |
| `run-start` | `turnId`、`runId`、时间。首次发出模型请求前写入。一次初始执行或显式继续产生一个 `runId`，单次模型重试沿用当前运行。已确认提交但缺少开始记录的回合等待用户启动。 |
| `stop-requested` | `turnId`、`runId`、时间、触发来源（`user-stop` 或 `host-shutdown`）。记录已接受的停止请求。每个运行以首次接受的请求为准。 |
| `tool-dispatched` | `turnId`、`runId`、assistant 消息记录 ID、`callId`、工具名、能力、时间。按助手消息和调用 ID 定位，避免跨回合的 Provider ID 复用产生冲突。记录存在表示工具可能已经启动。 |
| 工具结果的记录元数据 | 同一组标识及结果状态，区分实际结果和恢复合成结果。实际结果保存已有错误、拒绝状态和耗时。合成结果携带来源和证据等级。 |
| `run-end` | `turnId`、`runId`、终态、原因码、最后可确认的阶段、时间和记录来源（原进程写入或恢复推断）。完整最终回答与完成状态在同一条 assistant 消息记录里提交，重开可据此恢复完成状态。 |

以 v2 会话文件承载新契约。v2 读者继续读取 v1，对其历史未闭合工具组采用旧修复，并显示证据不足。v1 可以按原有方式追加。用户如需新版恢复能力，可从 v1 已修复历史新建 v2 会话副本，原文件仍可恢复。新版记录只写入 v2，老版本遇到 v2 通过现有版本检查干净拒绝。常规压缩写 checkpoint 并保留原始记录。未闭合的工具组先收尾，再进入压缩或模型请求。 [会话格式](../../../../packages/core/src/session.ts)

Core 的 Agent Loop 在权限判断和预览复查后、调用工具前等待宿主的派发写入回调成功，再检查取消信号。回调失败即结束本次运行。v2 可持久化运行必须有该回调，Desktop、TUI 和 headless 共用同一约束。派发、结果与恢复收尾都以会话写入方确认同步写入为边界。结果写入失败时停止发模型请求和派发后续工具。进程仍持有可信结果时，可按调用身份重新核对并仅补写该结果。已有 v1 和无持久化运行保留现行行为，相关宿主继续沿用自己的显示和退出约定。 [工具调用边界](../../../../packages/core/src/agent.ts) · [交互式审批](../../implemented/feature/2026-11-11-interactive-tool-approvals.md)

### 回合关闭原因

| 情形 | 终态和原因 |
| --- | --- |
| 用户点 Stop 或宿主进入正常退出流程 | 接受请求时记录触发来源，确认 Agent Loop 退出并记录已知工具结果后，写入 `stopped` 与对应原因。窗口断开而主进程仍在执行时，从主进程恢复运行态。 |
| 回合跑完、达到轮次上限或捕获无法恢复的错误 | 分别写入 `completed`、`limit-reached` 或 `failed`。失败附上已知阶段和稳定错误类别，例如模型请求失败或会话写入失败。可恢复的请求错误走同一运行的重试。 |
| 重开时仍有 `run-start` 而缺少终态，原运行已失去写入权 | 推断为 `interrupted`，原因 `unknown`。如果存在 `stop-requested`，额外显示已知触发来源，例如「用户请求停止，收尾未确认」。崩溃、强杀和断电的区分需要独立证据。 |

宿主只接受活动 `runId` 的停止请求。接收后先阻止新的模型请求和工具派发，再将停止标记交给有序写入队列，同时向当前操作发取消信号。写入失败时仍然发出取消，在界面说明记录可能缺失。停止请求与完成结果由同一运行协调。完成已确认时忽略迟到的停止。恢复时先生成只读状态，用户选择继续并取得写入权后才补记原运行的中断终态。工具的退出和副作用各自按已知证据记录。

### 中断证据与收尾

证据按调用身份核对。每个工具组在下一次 Provider 请求前都要校验调用和结果一一配对，并保留结果顺序。诊断和历史模型消息分开保存。查看会话时使用同一个纯函数构造内存视图，`loadSession` 保持只读。当前进程正常收尾时，持锁写入缺失项和终态。重启后的缺失项只在用户发起继续、取得写入权并重新加载以后物化。按调用身份查重，重复打开或继续生成同一组事实。若写入中途失败，下次重新核对已有记录。

| 持有的证据 | 恢复状态与处理 |
| --- | --- |
| 已有完整、身份匹配的实际结果 | 保留成功、失败、拒绝或取消及原有输出。常规工具错误写入结果后可交由模型处理。失败或取消时仍可能已经产生部分变更。 |
| 当前进程已封住派发入口，确认该调用未启动，或日志中已有明确的未执行记录 | 标作「未执行」，记录是因为停止还是批次失败。等待审批或复查时收到停止也走这里。 |
| 确认有派发记录，最终结果缺失 | 标作「结果未知」。调用可能仍在运行，也可能已经完成。 |
| 进程异常退出而缺乏未执行的正面证据，或尾部损坏、疑似断电、旧格式无法建立证据链 | 缺证据的调用标作「无法确认」。完整且身份匹配的已知结果照常保留。有效换行及 JSON 可解析只证明记录可读。 |

已开始的本地命令和远程工具都用同一恢复策略。原进程还在时，发送取消信号并按工具自身的取消和超时边界等待，界面显示「正在停止」。等待超时且无法确认退出时，显示「停止未确认」，把仍能跟踪的任务状态保留在界面。进程重启后按持久记录判定，进程 ID 不能证明副作用或存活结果。

有副作用风险的未知或无法确认调用需要用户显式选择继续。先提供只读核对，再由用户确认可以推进。历史工具调用作为事实读入上下文，避免把合成结果当成重新执行指令。恢复核对阶段由 Core 限制为只读，明确确认后的新执行仍走当前审批与预览。恢复时只还原 `plan` 或 `ask`，过期审批和进程级授权作废。TUI 与 headless 的 v2 读取也遵守这条核对边界。即使操作者显式选择 `auto`，有待核对的中断回合仍须先处理。第一阶段的「继续」交互由 Desktop 提供，其他宿主对有待核对的回合报告需要交互核对。 [运行时权限模式](../../implemented/feature/2026-11-09-runtime-permission-modes.md)

等待审批时点击「停止」会从现有的合成拒绝改为因停止而未执行。模型可见结果应明确是停止导致，继续后优先核对任务目的及已知状态。用户单独点击「拒绝」仍生成明确拒绝结果，保留现有拒绝语义。正常关窗走停止清理。重启时只有完整最终回答及相应完成记录能确认完成，崩溃后的开放运行显示「中断」。终态一旦确认保持稳定。迟到的真实结果只能按原调用身份补记为证据。若合成结果已经进入 Provider 上下文，补记通过后续宿主通知更新事实，保持已发送的历史不变。

### 单次模型请求的重试

- 三个适配器把错误归一化为临时传输或超时、临时过载或限流、鉴权或配置、硬配额、上下文超限、截断或协议错误。用可用的结构化状态和错误码区分限流与硬配额。未知类默认报告失败。OpenAI 两个适配器已经关闭 SDK 自动重试，Anthropic 在接入 Core 预算时同样显式设为零。
- 活进程中，本次请求尚未产生可见回答且无该请求引出的已提交动作时，可对临时错误自动重试。建议每个模型步骤最多三次采样，含初次请求和现有上下文压缩后的重新采样。临时故障采用约 1 秒、2 秒的可取消退避。供应商要求等待更长时间时，在总等待预算 15 秒内遵守，超出预算时显示原因与重试入口。
- 某个工具批次结果已经全部写入时，可以按原有上下文重试其后的模型请求。已输出部分回答时，界面保留它并标为中断，用户可选择「重试回答」。未完整提交的文本不作为完整 assistant 消息回放。已截断或协议不完整的响应不得派发其中的工具。重开应用只恢复状态，并等待用户再次发起工作。
- 重试等待和再次采样均属于同一个运行，期间只发进度事件。停止取消等待。预算耗尽、用户停止、达到 Agent Loop 轮次上限或完成时，各有明确终态。续传随恢复后的消息重新校验所有者和锚点，遵守原适配器的协议、端点和模型边界。 [协议续传](../../implemented/architecture/2026-11-12-reasoning-continuation-replay.md)

### Desktop 运行事件

`submit` 只确认用户输入已经入会话，回合进度走订阅事件。应按 `turnId`、`runId` 及运行内递增事件序号合并进度。窗口重连时通过 `getRunState(sessionId)` 读取当前运行及最近终态。按快照序号补接之后的事件。已确认终态只提交展示一次。

| 事件或操作 | 最小字段与语义 |
| --- | --- |
| 回合状态事件 | `sessionId`、`requestId`、`turnId`、`runId`、序号、阶段。阶段包括模型请求、重试等待、审批、工具、正在停止。重试等待带尝试次数和预计等待。 |
| 回合终态事件 | 同一组标识、`completed`、`stopped`、`interrupted`、`failed` 或 `limit-reached`，以及可展示原因和可用的恢复动作。 |
| `continueTurn(sessionId, turnId)` | 显式继续已接收的回合并返回新的 `runId`。主进程重新验证可继续性和写入权。已完成回合、被 rewind 撤下的回合、正在执行的同一回合以及待核对的高风险回合分别返回相应状态。 |
| `stop(runId)` | 指向明确的运行。接收后发「正在停止」，收尾后发布终态。旧运行的停止请求不会作用到新运行。 |

### 交付顺序

1. Desktop v1 的草稿和提交确认已经接入。
2. 先实现并验证会话写入互斥，同时用测试夹具实现 v2 回合记录的读取和终态推断。锁和平台验证完成后再启用 v2 写入。
3. 接入 v2 提交对账、停止和终态记录，验证写入成功但确认丢失，以及停止请求已记录但收尾前退出。
4. 补齐不完整工具批次的恢复和显式继续。单次模型请求重试可以独立开发验证，与运行状态事件一起接入。

## Implementation progress

Desktop 已接入 v2 接收确认、运行终态、Stop 和宿主退出原因、审批重连、逐调用恢复和显式继续。无终态且原写入权已释放的运行显示为中断，保留已观察到的停止请求。副作用结果未知时，先只读核对，再由操作者确认是否推进。TUI 与 headless 可在有锁时追加已完成的 v2 会话，待恢复回合通过 Desktop 处理。模型重试限制在可识别的临时连接、限流和服务故障，以及尚未输出文本或推理的请求。各平台端到端验收仍按下文清单推进。

## Alternatives considered

**重试整个用户回合。** 容易重复追加消息，并重新提出已有副作用的工具。Codex 从当前采样边界重建历史，Pi 使用已有会话继续采样。 [Codex 采样源码](https://github.com/openai/codex/blob/345f166d01fda88e6e723afbbfdce2efde843f74/codex-rs/core/src/session/turn.rs#L1977-L2019) · [Pi 重试源码](https://github.com/earendil-works/pi/blob/05fd3fbda0bbb9a1c7a76e4bf92ab58ed77c8d94/packages/coding-agent/src/core/agent-session.ts#L3932-L3975)

**丢弃整组或加载时直接补写。** 前者损失工具结果，后者让只读访问也竞争写入。采用按调用补齐的恢复视图，在收尾或显式继续时提交。 [DeepSeek Harness 恢复源码](https://github.com/deepseek-ai/deepseek-harness/blob/ca33fd6843b205e279c7ccb6cb73a472c78f5760/packages/core/session/src/repair.ts#L151-L193)

**给 v1 checkpoint 附带恢复数据。** 老客户端可能忽略关键数据并继续写入。v2 用版本边界明确隔开执行语义，接受旧客户端需要升级才能继续新版会话的成本。

**用进程 ID 或额外进程隔离推断工具结局。** Job Object 或其他进程生命周期机制有助于清理本地子进程。它们仍无法证明退出前是否写过文件，也无法确认远程结果。恢复保持证据分级，进程隔离可以独立推进。

## Acceptance criteria

- 故障注入覆盖审批等待、复查后派发前、派发记录写入失败、工具执行中、工具返回后但结果写入前，以及工具结果落盘后模型断线。在 Desktop、TUI 和 headless 的 v2 运行里验证派发失败会阻断执行，结果写入失败后不会继续推进。
- 同一组调用包含已记录成功的 `edit`、已派发但结果缺失的 `shell`、尚未启动的 `read`。正常停止与强杀分别测试。已证明未派发的 `read` 显示未执行，强杀后缺乏证据的项显示无法确认。只读加载前后文件字节一致，继续时每个调用最多补一个结果。
- 覆盖 401、硬配额、临时 429、过载、上下文超限、截断、前后可见文本断流、等待期间停止、达到轮次上限以及完成与停止竞争。重试过程只出现一次最终状态，预算内无空闲闪烁，旧用户消息只出现一次。
- 分别验证用户停止、正常退出、只断开窗口、停止记录写入失败、写入停止记录后强杀、缺少停止记录时强杀，以及完整回答已确认后的迟到停止。界面能区分已知的停止请求和已确认的回合终态，写入失败仍能取消当前操作。
- 覆盖 v1 旧文件、v2 读者及旧版本拒绝、日志尾部残缺、完整回答写入后进程退出。验证续传不跨协议、端点或模型，重启后不还原 `auto`，当前预览审批仍适用。
- 在 Windows、macOS 和 Linux 对比派发前同步写入前后的工具批次耗时，报告中位数与 P95。运行 `npm run typecheck` 和 `npm test`。

## Risks

工具副作用与会话文件之间缺少共同事务。损坏或断电之后，证据不足的调用会进入核对流程。合成结果可能促使模型再次提出已生效的操作，需靠明确的模型可见状态、只读核对和当前审批共同约束。磁盘同步会增加派发延迟，性能验收将决定后续能否安全优化写入边界。
